# 設計資料：データベース・アーキテクチャ

## 1. 技術選定と理由

| 項目 | 採用 | 理由 |
|---|---|---|
| 言語・UI | 素の JavaScript（ES Modules）＋自作の小さな DOM ヘルパー | ビルド工程・依存パッケージが不要で、10年後でもそのまま動く。サプライチェーンリスクがない。バンドル不要で Service Worker のキャッシュも単純。開発環境に Node.js が無くても開発・テストできる |
| 永続化 | IndexedDB（自作の薄いラッパー） | iOS Safari で大容量・バイナリ（写真）を扱える唯一の標準ストレージ。複数ストアをまたぐ**原子的トランザクション**が使える。localStorage はテーマ・表示モードなどの小さな表示用キャッシュにのみ使用 |
| 金額計算 | BigInt による銭単位整数＋有理数 | 浮動小数点誤差を完全に排除。割り切れない単価（1000円÷3個）も評価額は正確に保持し、表示時のみ丸める |
| ZIP | 自作（STORE 書き出し、STORE/DEFLATE 読み込み・CRC-32 検証） | 依存ゼロ。DEFLATE 展開はブラウザ標準の `DecompressionStream` |
| バーコード | 自作 EAN-13/EAN-8 デコーダ＋（あれば）`BarcodeDetector` | iOS Safari には BarcodeDetector API が無い。外部ライブラリに依存せず、外部通信もしない |
| オフライン | Service Worker（キャッシュ優先） | アプリ本体をキャッシュし、機内モードでも全機能が動く |
| テスト | 自作の最小テストランナー（ブラウザ実行） | 実ブラウザの IndexedDB で結合テストできる |

フレームワークを使わない代わりに、画面は「状態 → DOM を作り直す」単純な描画方式に統一しています（各画面は `{ el, update() }` を返し、データ変更時に `update()` が呼ばれる）。

## 3. データモデル

```
Division 1 ─── * Location 1 ─── * (op.locationId …)
Category 1 ─── * Item 1 ─── * Photo
                  Item 1 ─── * Op（receive / consume / move / adjust / void）
```

IndexedDB ストア（DB名 `zaiko-main`、サンプルは `zaiko-sample`）：

| ストア | キー | 索引 | 内容 |
|---|---|---|---|
| items | id | | 商品マスター |
| photos | id | itemId | 写真メタ情報（起動時に全件読み込み） |
| photoBlobs | id | | 写真本体 `{id, data: ArrayBuffer, thumb: ArrayBuffer}`（必要時のみ読み込み） |
| categories / locations / divisions | id | | マスター |
| ops | id | itemId | 在庫操作履歴（追記のみ） |
| meta | key | | `state`（revision・最終バックアップ等）、`settings` |

項目の詳細は [BACKUP_FORMAT.md](BACKUP_FORMAT.md) §3 と同一です（バックアップは DB の内容をそのまま書き出す）。

### 設計上の要点

- **商品マスターと購入履歴の分離**：購入価格・保管場所が違っても商品は1件。購入ごとに `receive` 操作（＝ロット）が作られる。
- **在庫数を保存しない（イベントソーシング）**：在庫数・ロット残数は常に ops を操作日順に再生して導出する。これにより、
  - 過去日付の操作の追加・訂正・取り消し後も、自動的に整合した結果になる。
  - 「在庫数カラムと履歴の食い違い」というクラスのバグが原理的に発生しない。
  - 個人利用の規模（数千〜数万件）では商品単位の再生は数ミリ秒。結果は商品単位でキャッシュし、変更時のみ無効化。
- **訂正・取り消しは追記**：元の操作は削除せず、`void`（取り消し）または `corrects`（訂正）レコードを追加する。訂正レコードは元の `order` を引き継ぐので、同日内の並び位置が変わらない。取り消しの取り消しも可能。
- **同日時の順序**：`(date, order, seq)` で一意に決まる。seq はデータセット内の通し番号。
- **棚卸しは「実数」を記録**：差分ではなく実際に数えた数を保存する。過去の操作を後から追加した場合、棚卸し以降の在庫は棚卸しの実数に合わせられる（棚卸し時点の実物が正しいため）。差分は再計算され、記録時の差分（recordedDelta）も参考として保持する。
- **移動**：ロットを場所間で分割して移す（`(lotId, locationId)` 単位で残数管理）。価格・入庫日は元ロットのまま。移動先での FIFO も元の入庫日順。

## 4. 整合性と安全性

| リスク | 対策 |
|---|---|
| 負数在庫・不正数量 | 保存前に必ず「既存履歴＋新操作」を再生し、どこか1か所でも矛盾があれば保存しない。数量は正の整数、日付は実在日・未来不可、金額は小数2桁までを検証 |
| 過去日付追加による後続の矛盾 | 再生で検出し「◯月◯日の使用で在庫が不足します」のように原因の操作を示して拒否。手動ロット指定も黙って変更しない |
| 同時操作 | すべての書き込みを直列キューで処理（連打・複数タブ）。他タブの変更は BroadcastChannel で通知し再読み込み |
| 途中失敗 | 1つの変更は1つの IndexedDB トランザクション。失敗時はブラウザが全体をロールバック（テストで確認済み） |
| 容量不足 | QuotaExceededError を検出し「データは変更されていません」と表示。写真は長辺1600px・JPEGに縮小。`navigator.storage.persist()` で永続化を要求 |
| 復元失敗 | 検証（ハッシュ・件数・参照・再生）を通らないファイルは取り込まない。置き換えも統合も1トランザクション |
| テストデータ混入 | サンプルは別 DB（`zaiko-sample`）。切り替え・リセットは本番 DB に一切触れない |
| 外部通信 | なし（Service Worker も同一オリジンのみ扱う）。CSV 出力は数式インジェクション対策済み |
| データ消失 | 手動バックアップ＋リマインダー（変更があり、設定日数経過時のみ）。保存成功を確認した場合のみ最終バックアップ日時を更新 |

## 5. 画面と主要フロー

- 在庫一覧：検索（正規化してAND検索：商品名・JAN・メーカー・型番・規格・メモ・カテゴリ・保管場所名）、絞り込みチップ、並び替え、リスト／カード（設定に保存）。数量部分をタップでクイック操作。
- 商品詳細：写真カルーセル、在庫（箱換算は参考表示）、場所別バー、入庫／使用／移動／棚卸しボタン、税込・税抜別の在庫金額と平均単価、ロット別残数、直近履歴。
- 操作シート：下からのシート（片手操作）。入庫は「箱・袋単位／バラ」入力、単価のリアルタイム計算。使用・移動は在庫のある場所をボタンで選択、FIFO／手動ロット指定。操作直後のトーストから取り消し。
- 履歴：日付別タイムライン。詳細から訂正・取り消し・取り消しの取り消し。訂正済・取消済・後日記録をバッジ表示。

## 6. 拡張性（将来のクラウド同期）

- すべてのレコードが UUID を持ち、ops は追記のみ・不変なので、端末間同期は「ops の和集合＋マスターの最終更新優先」で実装できる（統合復元と同じロジック。`planMerge` がそのまま流用可能）。
- `datasetId` と `revision` により差分検出の基盤がある。
